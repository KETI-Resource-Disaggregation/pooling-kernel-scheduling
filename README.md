# pooling-kernel-scheduling

**KRAKEN 엔진 — 커널·요청 수준 시공간 자원 공유 런타임**

AI 반도체 컴퓨팅 자원분해 및 자원풀링 기술 개발 (No.RS-2025-02220502)

가속기 한 장을 여러 테넌트가 나눠 쓰도록 **실행 경로에 개입해 시간과 공간을 배분**하는 런타임 계층이다.
GPU는 CUDA 호출을 가로채 커널 단위로, NPU는 벤더 런타임에 개입할 수 없어 요청 유입 경계에서 제어한다.

---

## 구성

| 경로 | 역할 |
|---|---|
| `libbless/` | CUDA 인터셉션 라이브러리 (LD_PRELOAD). 커널 실행·메모리 API 후킹, 토큰 버킷 시간 크레딧, 메모리 쿼터 |
| `gating/` | Killer-Op 게이팅 — 무거운 커널을 제출 전 CPU 블로킹 + 스트림 동기화 |
| `timeslice/` | 라운드 관리, 타임슬라이스 배분 |
| `resource/` | 가상 SM·가상 메모리 회계 |
| `hooks/` | CUDA / CUPTI 훅 |
| `npu_proxy/` | NPU 요청 게이트 코어 (`gate_core.py`) — 테넌트별 큐, 정규화 사용량 기반 선택 |
| `shm/` | 공유 메모리 클라이언트 (컨트롤러와 상태 공유) |

---

## 현재 구현 상태

### 동작 확인된 것

**GPU 시간 축**
- LD_PRELOAD 인터셉션, 메모리 쿼터 강제 — 실측 확인
- Killer-Op 게이팅 — 커널 제출 전 블로킹으로 간섭 완화
- 토큰 버킷 크레딧 배분, work-conserving 폴백 (크레딧 소진 시에도 대기 작업이 있으면 후순위로 서비스)

**GPU 공간 축**
- MPS `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` 위임 방식으로 SM 비율 제어 — 69:29 배분에서 처리량 2.29배
- 공간 분할만 적용 시 캡 손실이 선형보다 작음 (50% 캡 단독 = 전체 단독의 66.9%)

**NPU 요청 게이트** (`npu_proxy/gate_core.py`)
- 테넌트별 큐 + 정규화 사용량(사용량/몫) 최소 선택
- GPU 시간 게이트와 **동일 코어를 공유**하고 다루는 단위만 커널 → 요청으로 바뀜
- work-conserving 옵션 (기본 켬)
- 크레딧 잔고 상한을 환경 변수로 분리 — 이 값이 달성 가능한 비율 해상도를 정한다(아래)

### 측정으로 확인된 한계

| 항목 | 내용 |
|---|---|
| 제어 양자 | GPU 커널 1건(μs) vs NPU 요청 1건(약 565 ms) |
| 선점 | NPU는 실행 중 요청을 중단할 수 없음 |
| 크레딧 상한 | 상한이 요청 1건 실행시간보다 작으면 목표 비율이 무너짐 (달성률 43% → 98.6%, 7개 조건 예외 없음) |
| 유휴 회피 정책 | 극단 비율(약 76:24 이상)을 만들 수 없음. 정책을 끄면 가능하나 처리량 33% 손실 |
| 요청 길이 분산 | 길이가 섞이면 달성률 97.7% → 89%, 꼬리 지연 2.1배. **상한 조정으로 해결되지 않음** |

## 앞으로 할 것

- [ ] **요청 길이 분포를 반영한 몫 배분** — 현재 상한 기반 회계는 요청 길이가 고정일 때만 성립
- [ ] **꼬리 지연 악화 원인 규명** — 길이가 섞일 때 짧은 요청이 긴 요청 뒤에 갇히는지 요청 길이별로 계측
- [ ] **다른 이산 분할 하드웨어 검증** — 최소 코어 요구는 모델·아티팩트의 성질이므로 일반화 확인 필요
- [ ] **워크로드 다양성 확대** — 현재 검증은 모델 1종, 고정 프롬프트, 닫힌 루프 부하
- [ ] Command Buffer 파싱 (설계 잔여 항목)

## 빌드

```bash
cd libbless && make          # CUDA 인터셉션 라이브러리
```

요구 사항: CUDA 12.0 이상, Compute Capability 7.0 이상 NVIDIA GPU, Python 3.8 이상

> `.so` 산출물은 빌드 환경(드라이버·glibc)에 종속적이다. 배포 대상 노드에서 재빌드해야 한다.
